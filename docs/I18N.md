### Resolução de Texto (Campo a Campo)

A regra fundamental é **fallback campo a campo**:

```
Idioma pedido → se tem tradução do campo → usa tradução
             → senão → usa valor pt-BR (fallback)
             → marca `fallback=true` na resposta
```

Isso significa que um produto pode ter:
- Nome traduzido
- Descrição em pt-BR (fallback)
- Atributos parcialmente traduzidos

### Tabela `product_translations`

```sql
product_translations (
    product_id    UUID  NOT NULL,
    locale        VARCHAR(10) NOT NULL,  -- en, es, ar
    name          VARCHAR(200),
    description   TEXT,
    attributes    JSONB,                  -- apenas valores de texto traduzidos
    source_hash   CHAR(64) NOT NULL,      -- SHA-256 do conteúdo pt-BR
    status        VARCHAR(16) NOT NULL,   -- machine | reviewed | stale
    translated_at TIMESTAMPTZ,
    PRIMARY KEY (product_id, locale)
)
```

- **`source_hash`**: Hash determinístico (SHA-256) do conteúdo de origem (nome + descrição + atributos de texto em pt-BR). Usado para detectar quando a origem mudou.
- **`status`**:
  - `machine`: Gerada automaticamente (seed ou futuro provedor), não revisada por humano.
  - `reviewed`: Revisada/confirmada por humano via admin.
  - `stale`: A origem pt-BR mudou após a tradução ser gerada. **A tradução continua sendo servida** até ser atualizada (não se perde conteúdo).
- **`translated_at`**: Timestamp de quando a tradução foi criada/atualizada.

### Dicionários Versionados (Arquivos JSON)

Além das traduções de produto, existem dois dicionários globais versionados no repositório:

1. **`app/infrastructure/i18n/category_names.json`**: Nomes de categorias por slug e locale.
2. **`app/infrastructure/i18n/attribute_dictionary.json`**: Rótulos (`labels`) e opções (`options`) de atributos por locale.

Estes são carregados via cache LRU (`load_category_names`, `load_attribute_dictionary`) e usados como fallback implícito: se não há entrada no dicionário para um locale, usa-se o valor original (pt-BR).

## API

### Negociação de Locale

O locale é resolvido na seguinte ordem de prioridade:

1. **Query parameter `?lang=`** (ex: `?lang=es`)
2. **Header `Accept-Language`** (ex: `Accept-Language: en-US,en;q=0.9`)
3. **Default**: `pt-BR`

**Valor inválido cai no default sem erro** (retorna pt-BR). O cliente deve reenviar um `?lang=` válido se quiser outro idioma.

### Respostas

Todas as respostas de catálogo, busca, carrinho e pedidos incluem:

```json
{
  "name": "Translated Name",
  "description": "Translated description",
  "attributes": [
    {"key": "cor", "label": "Color", "value": "white", "unit": null}
  ],
  "content_locale": "en",
  "fallback": false
}
```

- **`content_locale`**: Idioma efetivamente entregue (pode ser `pt-BR` se houve fallback total).
- **`fallback`**: `true` se **pelo menos um campo** veio do pt-BR.

## Busca Multilíngue (Fase 9B-b)

### Índice Elasticsearch

A partir da **versão 2 do índice** (`elasticsearch_index_version = 2`), o mapping inclui campos dedicados por idioma com analisadores nativos:

| Campo | Idioma | Analisador |
|-------|--------|------------|
| `name`, `description` | pt-BR (origem) | `pt_text` (stemmer português + ascii_folding) |
| `name_en`, `description_en`, `attributes_text_en` | Inglês | `en_text` (stemmer inglês + ascii_folding) |
| `name_es`, `description_es`, `attributes_text_es` | Espanhol | `es_text` (stemmer espanhol + ascii_folding) |
| `name_ar`, `description_ar`, `attributes_text_ar` | Árabe | `ar_text` (arabic_normalization + stemmer árabe) |

- **`dynamic: strict`**: Apenas campos explícitos no mapping são indexados.
- **Sem preço, sem dados privados**: O documento indexado NÃO contém preço, estoque, CPF/CNPJ, senhas ou dados de pagamento.
- **Disponibilidade derivada**: `is_available` reflete `status=ACTIVE` + CA válido (para EPI) no momento da indexação; não é armazenado no PostgreSQL.

### Consulta

O construtor de consultas (`ElasticsearchProductIndex._build_text_query`) busca nos campos do **idioma do cliente E nos de pt-BR**:

```python
# Prioridade (boosts):
1. SKU exato (boost 10) — todos os idiomas
2. Prefixo SKU (boost 8) — todos os idiomas
3. Frase no nome do cliente (boost 6) + pt-BR (boost 6)
4. Termos fuzzy no nome do cliente (boost 4, fuzziness AUTO) + pt-BR (boost 4)
5. Categoria/Marca/Descrição pt-BR (boost 2/2/1)
6. description_locale / attributes_text_locale (boost 1)
```

**Comportamentos:**
- Locale não suportado (ex.: `fr`, `de`) → usa apenas campos pt-BR; não quebra.
- pt-BR (idioma de origem) → usa apenas campos base; não duplica.
- Fuzziness `AUTO` **apenas** nos matches de `name` (pt-BR e locale), **nunca** no SKU.
- Filtros obrigatórios: `status=ACTIVE`, `is_available=True` + facets opcionais.
- Paginação e limites mantidos (via `SearchQuery`).

### Hidratação e Autorização (Mantido)

- Busca retorna apenas IDs; `SearchProducts.run()` hidrata do PostgreSQL via `ProductReader.get_products_by_ids()`.
- Preços resolvidos por `resolve_company_price` (visitante = `price_on_request: true`; autenticado = preço por empresa/regra).
- Autorização via `AuthContext` (tenant do JWT, RBAC).
- **Fallback PostgreSQL textual continua em português** (limitação: busca textual no banco não usa traduções).

### Embeddings (Mantido)

- `build_embedding_text()` usa apenas texto de origem pt-BR (nome, marca, categoria, descrição).
- Modelo multilíngue (`intfloat/multilingual-e5-small`) cobre outros idiomas; **não gera embeddings por idioma**.
- `content_hash` inclui modelo + texto; backfill idempotente.

### Sincronização

O mecanismo de eventos existente (`DispatchSearchOutbox`, `ReconcileSearchIndex`, `ReindexProducts`) já propaga traduções:

- **Outbox UPSERT** (edição de tradução manual, seed, `stale`): Reaplica `build_product_document()` que lê `translations` do `ProductRow` → atualiza campos `name_{locale}`, `description_{locale}`, `attributes_text_{locale}` no índice.
- **Outbox DELETE** (despublicar): Remove documento completo do índice.
- **Reconcile**: Compara versões (epoch ms de `updated_at`). Se versão no Postgres > índice → reindexa com traduções atuais.
- **Reindexação**: Cria índice versionado (`forja_products_vN`), valida contagem (tolerância 0 por padrão), troca alias atomicamente, **mantém índice anterior para rollback**.

### Limitações (Atualizadas)

1. **Árabe não revisado por falante nativo**: Traduções de `ar` são de máquina/automatizadas. Validar antes de uso em produção.
2. **Sem tradução automática no request**: Nenhum serviço externo é chamado no caminho de leitura.

7. **Embeddings só em pt-BR**: Modelo multilíngue cobre outros idiomas, mas embeddings são gerados apenas do texto pt-BR.

## Porta `TranslationProvider`

### Design

Não há provedor de tradução adotado nesta fase. A arquitetura define uma **porta** (interface) para permitir decisão futura sem acoplar o domínio:

```python
# app/application/ports/translation.py
class TranslationProvider(Protocol):
    @property
    def name(self) -> str: ...
    @property
    def enabled(self) -> bool: ...
    async def translate(self, request: TranslationRequest) -> TranslationResult | None: ...

class NullTranslationProvider:
    name = "null"
    enabled = False
    async def translate(self, request): return None
```

- **`NullTranslationProvider`** (padrão): Não traduz nada. Mantém o fluxo admin funcional (edição manual + revisão).
- Quando um provedor real for configurado (ex: API de tradução, LLM, modelo local), ele **apenas gera/atualiza traduções offline** via processo de background/admin. **Nunca no caminho de leitura do cliente.**

### Configuração

```bash
# .env
TRANSLATION_PROVIDER=null  # ou nome do provedor futuro
```

## Admin de Traduções

### Endpoints (RBAC: ADMIN)

| Método | Endpoint | Descrição |
|--------|----------|-----------|
| `GET` | `/api/v1/admin/catalog/translations/products/{product_id}` | Lista todas as traduções do produto com status e `is_stale` |
| `PATCH` | `/api/v1/admin/catalog/translations/products/{product_id}/{locale}` | Edita tradução manualmente, opcionalmente marca `mark_reviewed=true` |

### Fluxo `stale`

1. Admin edita produto em pt-BR (nome, descrição ou atributos de texto).
2. Seed/próxima execução detecta `source_hash` divergente → marca traduções existentes como `stale`.
3. Tradução `stale` **continua sendo servida** aos clientes.
4. Admin visualiza `/translations/products/{id}` → vê `is_stale=true`.
5. Admin edita tradução manualmente via `PATCH` + `mark_reviewed=true` → status volta a `reviewed`.

### Edição em pt-BR Gera `stale`

No caso de uso `UpdateProduct` (admin), ao alterar campos de texto do produto, as traduções existentes **não são alteradas automaticamente**. O `source_hash` novo será diferente do armazenado nas traduções, fazendo `is_translation_stale()` retornar `True` na próxima leitura.

## Seed de Demonstração

Arquivo: `backend/app/seed_data/demo_translations.json`

```json
{
  "locales": ["en", "es", "ar"],
  "products": {
    "SKU": {
      "en": {"name": "...", "description": "...", "attributes": {...}},
      "es": {"name": "...", "description": "...", "attributes": {...}},
      "ar": {"name": "...", "description": "...", "attributes": {...}}
    }
  }
}
```

- **Idempotente**: Re-executar o seed mantém o mesmo resultado (`ON CONFLICT DO UPDATE`).
- **Status**: `machine` (não revisado por falante nativo).
- **Preservação exata**: Números, unidades, códigos (CA, SKU, medidas como `20V`, `850W`, `100L`, `7 1/4`, `15T`, `2cv`) são **preservados exatamente** como na origem. Marcas, SKUs, CA **não são traduzidos**.
- **Qualidade**: Especialmente o árabe **não foi revisado por falante nativo**. Use com cautela em produção.

## Como Adicionar um Novo Idioma

1. **Adicione o locale em `SUPPORTED_LOCALES`** (`.env` ou `settings.supported_locales`):
   ```bash
   SUPPORTED_LOCALES=pt-BR,en,es,ar,fr
   ```

2. **Adicione traduções de categorias** em `app/infrastructure/i18n/category_names.json`:
   ```json
   { "fr": { "protecao-cabeca": "Protection de la Tête", ... } }
   ```

3. **Adicione rótulos/opções de atributos** em `app/infrastructure/i18n/attribute_dictionary.json`:
   ```json
   { "labels": { "fr": { "cor": "Couleur", ... } }, "options": { "fr": { ... } } }
   ```

4. **Traduza o catálogo de demonstração** (opcional): Adicione locale `fr` em `backend/app/seed_data/demo_translations.json` para cada produto.

5. **Rode o seed** para popular `product_translations`:
   ```bash
   python -m app.infrastructure.db.seeds
   ```

6. **Configure provedor de tradução** (opcional): Se houver provedor externo, implemente `TranslationProvider` e configure `TRANSLATION_PROVIDER`.

## Frontend Multilíngue (Fase 9B-c)

### Resumo
O frontend Next.js (App Router + `next-intl` v3) exibe o catálogo, busca, carrinho e pedidos no idioma escolhido pelo cliente, com layout RTL para árabe e indicadores visuais de `content_locale`/`fallback`.

### Arquitetura Frontend

**Roteamento e Locale:**
- Roteamento por locale: `/[locale]/...` com `localePrefix: "always"`
- Middleware `next-intl/middleware` gerencia roteamento i18n
- `useTranslations()` hook para componentes cliente, `getTranslations()` para Server Components
- Locale padrão: `pt-BR`; 11 locales suportados (pt-BR, en, zh-CN, ja, ko, ru, es, de, fr, it, ar)
- Seletor de idioma no header (`LanguageSwitcher`) com preferência persistida em cookie

**Infraestrutura de Idioma:**
- `HttpRequest` aceita `locale?: string` → envia header `Accept-Language`
- `FetchHttpClient` adiciona `Accept-Language` quando locale fornecido
- API adapters (`catalogApi`, `cartApi`, `orderingApi`, `creditApi`, `companyApi`) recebem `locale` e expõem hooks `useCatalogApi`, `useCartApi`, `useOrderingApi`, `useCreditApi`, `useCompanyApi` que injetam `useLocale()` automaticamente

**Indicadores Visuais de `content_locale` e Fallback:**
- `ProductDetailView`: Exibe ícone Globe + código do locale + badge "Fallback" (âmbar) quando `content_locale !== locale` e `fallback=true`
- `CartView`: Mesmo indicador por item do carrinho
- `OrderDetailView`: Indicador no cabeçalho do pedido + por item
- Chaves de tradução: `catalog.translationFallback`, `catalog.translationExact`, `catalog.fallback` (11 locales)

**Indicadores Visuais de `content_locale` e Fallback (atualizado V3):**
- `ProductDetailView`: Exibe ícone Globe + código do locale. **Quando `content_locale !== locale`, mostra nota discreta "Conteúdo exibido em {locale}"** (chave `catalog.contentDisplayedIn`).
- `CartView` e `OrderDetailView`: **Sem indicadores de fallback** (removidos na V3).
- Chaves de tradução: `catalog.translationFallback`, `catalog.translationExact`, `catalog.contentDisplayedIn` (11 locales).

**RTL para Árabe:**
- `html lang` e `dir="rtl"` no documento quando locale `ar` (`layout.tsx`)
- Font stack inclui `Noto Sans Arabic` (`tailwind.config.ts`)
- Propriedades lógicas CSS: `ms-1` (margin-inline-start), `text-end` (text-align: end), `text-start` (text-align: start)
- Componentes Radix UI (Select, DropdownMenu, Dialog) funcionam com `dir="rtl"` via CSS
- **Numerais**: Ocidentais (1, 2, 3) adotados para consistência com BRL e dados técnicos; árabe-índicos (١, ٢, ٣) não usados
- **Auditoria de classes físicas**: 36 ocorrências em admin (excluído), 20 em shared UI (Radix internos). Zero em telas do cliente.

**Admin "Traduções" (Seção 5 do formulário de produto):**

- Lista traduções por locale com badges de estado: `ausente`, `machine`, `reviewed`, `stale`
